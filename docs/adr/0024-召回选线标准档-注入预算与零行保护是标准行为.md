# ADR-0024 召回选线「标准档」：注入预算与零行保护是标准行为，不是可配置项

- **状态**：已接受（2026-11-03；来源：用户令「分析记忆召回正确率低的根本原因，结合主流记忆系统重构召回算法」+「尽量不要加新的配置项，最优记忆召回不是可配置的而是标准」）
- **关联**：规格 `docs/specs/2026-11-02-recall-selection-layered-ruler-spec.md`（§4.0 不变量、§4.3 配置面、§4.8 零行保护、§4.9 证据窗）；复现实验数据 `.eval-data/bench/bench-longmemeval-oracle-20261103-*.json`
- **域词典**：`CONTEXT.md` → 候选池 vs 注入行、意图预算（budgetByIntent）、地板（floor）、证据窗（evidence window）

## 背景

LongMemEval-90（`lme-manifest.json`，seed 20261027，oracle 检索）在同一判官（scm-flash / lme-v2）、同一库、只改注入面的条件下：

| 注入预算 maxChars | genCorrect | refused | blockChars |
| ----------------- | ---------- | ------- | ---------- |
| 600（旧生产档）   | 0.400      | 52.2%   | 750        |
| 1200              | 0.667      | 25.6%   | 1239       |
| 1600              | 0.744      | 16.7%   | 1613       |
| 2400              | **0.778**  | 16.7%   | 2409       |
| 3600              | 0.789      | 14.4%   | 3267       |

检索面五档逐位相同（sessionCov 0.961 / turnCov 0.907 / MRR 0.769 / nDCG 0.809）——**瓶颈完全在读侧注入面，不在召回算法本身**。三处病灶：

1. **空块**：13/90 题 `blockChars=0`（12 道 single-session-assistant + 1 道 temporal），13/13 拒答。链路：`isAssistantRecallQuery` 判 `self` → `budgetByIntent.self=1` 只留首行 → 首行 692–3541 字 > 600 预算 → `layer-ruler` 整行丢弃不补位 → 零行纪律输出空块。
2. **检索到却没渲染**：50/90 题有金标轮已进入判定集却没进块，其中 41 题答错 = 全部错题的 75.9%。
3. **固定前言吃预算**：`answer-guidance` 413 字占块字符 p50 的 47.3%。

外部先例（见 ADR 关联的调研底稿）：LongMemEval 原文即指出「perfect recall 下读侧仍掉 up to 10 points」、且「用摘要/事实替代原轮次会因信息损失降低 QA」；Zep/Graphiti 把事实边+双时态直接渲染，Mem0 注入带时间戳，均为「读侧渲染」问题而非写入问题。

## 决定

1. **`injection.maxChars` 代码缺省 2400**（不再要求部署方填数字）。曲线在 2400 处折价：2400→3600 每 1000 字只买 +1 个百分点。
2. **`budgetByIntent` 标准档 `{empty:0, continuation:1, self:null, info:null}`**：`self:1` 的假设（「交互式上文已有」）在单轮 QA/自指场景自相矛盾；实测单改 self（a2）只 +1.1 pt，但它与预算叠加时决定 13 题生死。
3. **零行保护 = 标准行为，无开关**：enforce 且池非空、意图非 empty/continuation 时，若判定集为空，保回「渲染后装得进 maxChars」的最高分行；允许低于地板（地板是排序启发式，不是正确性闸门）；打分诚实记账（`selection.rescued` + `candidates.lines[].rescued`）。
4. **证据窗 = 标准行为，无开关**：整行绝对装不进预算时，换成「头 35% + 命中窗 40% + 尾 25%」节选（锚必须完整保留），绝不整行丢弃。**不做句级压缩**——证据集实验（句级压到 160 字）把 0.40 打到 0.20，19/19 净损失题都是「答案短语在截断点之后」。
5. **显式 `null` 仍是唯一回滚通道**；`mode: off` 与改动前逐位一致（证据窗、零行保护在 off 下都不生效）；写错的值（负数/非数字）回落标准档并告警，不再静默翻译成「不限」。
6. **折叠不得把保护打回 0 行**：同回合已注入导致 fold 删空时，保留被保护的那一行——空块比重复更糟。

## 后果

- 注入块字符 p50 从 750 涨到 2409（约 3.2 倍 token），换来 genCorrect +37.8 pt、refused −35.5 pt。以「每 1000 字符买到的正确率」计，600→2400 区间仍是正收益。
- 生产 `D:/TDB/data/config-override.json` 仍是 600 档 / self:1，属**部署值**：改它需要点名数值后另行执行（用户红线：生产配置不自行改动）。
- 观测面新增两个字段（`rescued`/`windowed`），journal 消费方需要兼容可选字段。
- 与其他读侧机制边界：证据窗不碰 soul/前言/wrapper，不改 `maxChars` 上限；与 `conclusionLayer` 自带的 `maxCharsPerMemory` 截断互不接管。

## 2026-11-03 增补：残预算回填上线 + 连续窗假设被实测否决

**决定（第 7 条）**：字符预算的「装不下就丢」再多走一步——被 `chars` 丢掉的候选，按分数降序
用证据窗裁到**剩余预算**回填（`injection-stage.ts:582-614`，无配置键、`mode:off` 不触发）。
它只用零头预算、不移除任何已选行，结构上不可能让已有证据变差；`BACKFILL_MIN_CHARS=200` 是
「够不够表达一件事」的下限，低于它宁可空着。

**否决（第 8 条）**：把证据窗改成「轻度超预算时切连续窗（头 80/20、60/40）」——两臂实测
70/90、70/90 均低于基线 71/90，refused 从 15.6% 升到 17.8%/18.9%。原因是固定比例的切口
必然切掉某一位置的答案，而三段窗的命中段恰好覆盖 35–75% 这一高发区。**不引入新窗口策略**。

**同时被否的度量习惯**：arm1 的 4 个 WIN 中有 3 个是「块完全相同、答案不同」，属 LLM 采样噪声；
本 bench 单臂噪声约 ±2–4 题，±1 的臂差不得当作改动效果——判据必须是机制题（块内文本变化）
＋逐题证据，这条应作为后续所有读侧 A/B 的纪律。

**口径上限（写入规格 §4.12）**：终态臂（arm3）块利用率 p50 已达 2647/2834、54/90 题 ≥90%，
预算不是约束；19 道错题按证据位置分 BLOCK 7（证据在块内仍错）/ RENDER 2（读侧可动）/
RETRIEVE 6（需 rerank）/ 词面不可判 4。读侧选线即使全对也只到 73/90 = 81.1%，
因此 ADR-0024 的 0.85 目标不是「再调预算/再调参数」可达，必须动答案口径（BLOCK 类）或排名
（RETRIEVE 类，rerank ORT 崩溃域），两者都在本轮授权范围之外。

## 2026-11-03 增补二：精排接管选行，但**不再接管呈现顺序**

**决定（第 9 条）**：rerank 生效时，块内行序**恒回融合序**（`auto-recall.ts` `applyRecallRerank` 内
`:935` 之后的 `presentIdxs`），journal 记 `gates.rerank.presentation: "fusion"`。精排的职责只剩
「哪些行进集合」。无配置键；`mode:"filter"` 本就保原序，行为不变。

理由（实测，非推断）：交叉编码器在本库上「会挑集合、不会排序次」。它的分序把决定性证据从块首推到
块中，而块内注意力先验是融合序。三臂（LME oracle 90 题、同 judge、串行、同库）：

| 选行 / 呈现              | genCorrect        | refused | turnCov | sessionCov | nDCG  | injectedLines |
| ------------------------ | ----------------- | ------- | ------- | ---------- | ----- | ------------- |
| 融合 / 融合（step3）     | 71/90 = 78.9%     | 15.6%   | 87.7%   | 96.1%      | 0.809 | 6.84          |
| 精排 / 精排（step5）     | 66/90 = 73.3%     | 17.8%   | 92.1%   | —          | —     | 7.93          |
| 精排 / **融合**（step9） | **72/90 = 80.0%** | 17.8%   | 91.6%   | 98.9%      | 0.837 | 8.01          |

精排-融合 vs 精排-精排 **9 胜 3 负**（超噪声带）；vs 融合-融合 3 胜 2 负（打平）但检索指标全面更好。

**决定（第 10 条）**：精排生效时**停用** `dynamicTopK` 的 elbow 收缩（门槛 `!rerankApplied`）。
elbow 依赖分数序列名次单调，而精排只平行重排原融合分、不重算分，几何前提已失效——不修会把注入从
10 行砍到 4 行（031748ae 实测，落差 0.222 = span 的 103%）。rerank 关断时逐位不变。

**否决（第 11 条）**：把注入行按行首时间戳排序（`recall.injectTimeSort`）在当前块格式下有害。
`inject-order.ts:15-18` 的行首正则对生产行格式 `- [episodic|bench] [ts] …` 永不匹配（历史上是 no-op），
修正后开跑：66/90，knowledge-update **12→8** 崩。跨会话行的时间交错破坏「同一事实的会话内连续性」。
已回退，代码保持 no-op 现状（不改正则）。

**被证伪的辅助假设**：证据包（`evidencePack`）在本数据集 inert（`seedWithSession:0`，种子行无 session
映射），其 +1 题为噪声；"行数不够"也不成立——injectedLines 6.84→5.30→7.93 与 genCorrect 71→68→66
同向恶化。

**剩余到 0.85 的缺口（诚实边界）**：终态 72/90 = 80.0%，refused 16/90。拒答的 16 例里只有 4 例
`evidenceSufficiency > 0.5`，其余是真缺证据：多跳/聚合题（年龄差 33、小时差、金额和、件数）所需的
**第二跳记忆根本没被召回**（e8a79c70 / 18dcd5a5 / eaca4986 / 71017277 命中只来自 1 个会话、仅 2–3 条）。
要继续往上必须动**多跳召回**（查询改写 / 会话级扩展召回），那是新能力而不是选线与预算参数；
读侧选线在 0.85 上的算术上限已在规格 §4.12 给出（81.1%）。

**上一条（残预算回填）终态实测**：step3-backfill-only = 71/90 = 78.9%，refused 15.6%，与基线逐题同分
（仅 gpt4_b4a80587 得一、7405e8b1 失一，属已知噪声题）。即残预算回填**无增益但不劣**：
它只在 6/90 题上改变了块文本，其余 84 题剩余预算 < 200 字。

## 2026-11-04 增补三：本地精排的「实测最优」写成代码缺省，并用硬预算兜住假死

**决定（第 12 条）**：本地精排推理的缺省参数 = 本机实测最优，写死在
`MemoryCore/src/core/recall/rerank/tuning.ts`：**2 线程 / 单条截断 320 字符 / 单次推理硬预算 6s**。
理由（32 候选实测）：线程 1/2/4/8 = 3257/**1939**/3245/3850ms（只有 2 线程有收益）；
耗时随「候选数 × 文档前缀长度」近似线性（200/400/800/1200/2000 字符 = 1680/3441/6546/7770/6816ms）；
batch 前向**无收益**（400 字符 3564ms vs 单条 3175ms，CPU q8 下 padding 吃掉并行）故否决。
env（`RERANK_THREADS` / `RERANK_DOC_CAP` / `TDAI_RERANK_INFER_TIMEOUT_MS`）只留给 A/B 与故障复现，
生产不配任何键即最优点——沿用「最优即标准，不摊成配置项」。

**决定（第 13 条）**：`--rerank-timeout` 对 local provider 必须生效（同时写
`config.rerank.timeoutMs` 与 `TDAI_RERANK_INFER_TIMEOUT_MS`）。旧实现里该键只作用于云端 fetch，
local 走 worker 推理，命令行传参**静默无效**——这正是「两次完整臂都撞 60s」时排查受阻的原因之一。

**决定（第 14 条）**：推理硬预算从 30s 收到 6s（生产争抢实测 3.81s 的 1.57×；4s 只剩 0.2s 余量会误降级）。30s 的旧缺省让**一次**假死就能吃穿插件侧
`recallTimeoutMs=2500` 与 v3 的 5000ms 超时；收紧后最坏是「本次降级原序 + 熔断计数」，不会拖死召回。

**验收（一步到位）**：同 90 题同判官同库，`step12-rerank-tuned`
（`.eval-data/bench/bench-longmemeval-oracle-20261103-165006-1eb3ab4c.json`）：
genCorrect **72/90 = 80.0%（与无提速档逐题相同）**、refused 15.6%、turnCov 93.6%（全臂最高）、
sessionCov 98.9%、端到端召回 mean 1657 / p50 1451 / p95 3173 / max 5696ms；
`gates.rerank.ms` p50 **299ms** / p95 765ms / max 1944ms（旧 p50 4515 / max 14305），
90 题 rerank 累计 485s → **31.7s**；此前超时退出的 4b24c848、06db6396 两题本轮均判对。

**生产生效（2026-11-04 00:54，用户当场授权重启）**：`/health` 的 `warmup.rerankMs` 从 0 → **2333**；
真实召回 journal 首条记录 `gates.rerank = {provider:"local", ms:3810, kept:2, dropped:29, presentation:"fusion"}`。
3.8s 的成因是重启后 pipeline boot recovery 重挂 406 会话的 CPU 争抢（空载实测同档 1.7–2.5s），
故硬预算按争抢实测值取 6s（1.57×）——留出争抢余量，同时仍是旧缺省 30s 的 1/5。

**教训（写进纪律）**：B2a/B2-b 早就加了 `RERANK_THREADS` / `RERANK_DOC_CAP` 两个提速开关，但缺省 `0`
（关闭）——于是「实验里验证过的优化」在真实路径上从来没生效，arm9 仍跑在 4.5s/题的未提速路径上。
提速类改动**不许以「默认关闭的开关」形态交付**：要么实测最优直接做缺省，要么不进主干。

## 2026-11-04 增补四：注入预算标准档 2400 → 6000（重标定），并钉死三条「让预算花得出去」的机制

**问题（旧边际点结论被逐题证据推翻）**：11-03 的标定曲线（1600 → 0.744、2400 → 0.778、
3600 → 0.789）得出「2400 之后每 +1000 字只买 +1 个百分点」，据此把 2400 写成标准档。
11-04 逐题取证发现曲线的**解释错了**：那时预算根本花不出去——块预算被「一条长轮次」吃满。
61f8c8f8（5K 提速）的候选池 10 条、金标轮排第 1，最终块里**一条该会话的行都没有**，因为
同会话一条 ~1200 字的 assistant 长回答独占预算，块只装得下 3 行、剩余预算记 1287 字空转。
在这种形态下加预算只是给那条长轮更多铺陈空间，当然买不到覆盖。

**决定（第 15 条）：maxChars 标准档 = 6000**，写死在
`MemoryCore/src/config.ts`（`STANDARD_INJECTION_MAX_CHARS = 6000`，injection 组内常量）。
三种显式写法语义不变：`null` = 不限（唯一回滚通道）、`0` = 硬零预算、负数/非数字 = 写错回落 + 告警。

**决定（第 16 条）：让预算花得出去的三条机制都是代码缺省，无配置键**

1. **证据窗单行份额 3/5**：`injection-stage.ts:370-375`（`LINE_SHARE_NUM/DEN`）。窗预算 =
   `min(maxChars, max(200, ⌊maxChars×3/5⌋))`；`expandKeptWindows` 的回填目标同样按 3/5 收口
   （`injection-stage.ts:757`）。**被否决形态**：给每条超预算行「全量 maxChars」——win 臂实测
   一条 3000 字长轮窗一填满就独占整块（afdc33df/35a27287 的块从 5–6 行塌成 1 行，偏好题其它证据全灭）。
2. **跨会话份额 3/5**：`layer-ruler.ts:39-40`（`SESSION_SHARE_NUM/DEN`），字符预算步里单个来源会话
   最多吃 3/5，只在候选跨 ≥2 会话时生效（`:64`）。依据 = 9 道 multi-session 错题中 6 道「两会话都进池、
   块里只有一个会话」。
3. **残预算回填 + 窗填满**（§4.10 的终态）：装填后仍有 ≥200 字预算时，把已入选的窗行按份额扩回；
   否则残预算空转（旧实现的 6/90 题块文本因此与基线一字不差）。

三条机制合起来才把「加预算」翻译成「加不同来源的证据条数」：同一 2400 字预算从 1–5 行变成 9–10 行，
6000 字预算则装 8 行（`injectedLines=8.0`）且块字符 5817（接近用满）。

**决定（第 17 条）：旧「3600 → 0.789 的边际点」结论标记作废**。它测于回填/窗填满/会话份额之前，

## 2026-11-04 增补五：精排尾延迟改「滚动打分预算」，并勘误本节末尾的 p95 结论

**问题**。上节留了两个尾巴：① 精排 p95 在 0.7–1.14s 之间漂移，只有在无并发争用的两臂才 <1s，据此写下
「不宣称稳定 <1s」；② `gates.rerank.ms` 是整池单次打分的时间，池子大小 × 单条长度 × 机器争用三者相乘，
单点读数没有可预期性（隔离压测：32 候选 × 320 字符连打 40 次，p50 1764ms / p90 5227ms，第 18 次打穿 4s
`inferTimeoutMs` 直接返回 null）。用户授权把尾延迟真正调稳，而不是换口径解释。

**决定 18（滚动打分预算，无配置键）**。本地 provider 不再整池单次打分，改为**按块滚动**：
`MemoryCore/src/core/recall/rerank/score-budget.ts` 的 `RERANK_SCORE_BUDGET_MS = 400`、
`RERANK_SCORE_CHUNK = 4`、`RERANK_CHUNK_SLACK_MS = 250`；`rerankWithinBudget()` 首块无条件跑，之后
每块开跑前检查 `elapsed > budgetMs`，到点即停；**已评块全部保留**，未评候选按融合原序垫尾（`unscored`
进观测面）。池子 ≤4 条时退化为单次整池调用（拆块只多付调用开销）。云 provider 保持单次（延迟由 RTT 主导）。
⇒ 精排尾延迟从「由池子大小决定」变成「由预算决定」，理论上限 = 400 + 250 = 650ms。

**决定 19（冷启动移出预算）**。`LocalReranker.warmup()` 必须在打分前 await：模型加载实测 1430ms，
若算进首块 400ms 预算，首块必被判超时 ⇒ 整题丢精排。armR4 的反面证据：v3（无 warmup）表面 genCorrect
92.2%、ms p50 0，但 **90 题里 61 题 `gates.rerank.ms=0`**（kept=pool、docs=pool），日志 13 次
「provider=local 返回 null，降级原序」——冷启动撞首块预算 → 3 题连超时 → 熔断 open → 后 61 题根本没精排。
该臂的质量数不可用作预算机制的 A/B。

**决定 20（超时不取消在途推理）**。曾实现 `cancelPending()`：软超时后 terminate worker 丢弃在途推理。
**实测在 onnxruntime 推理进行中 terminate 会让进程原生崩溃**：同一 90 题臂两次 exit 127、无任何 JS 报错，
二分到唯一差异就是这次 terminate（`scripts/lib/bench/rerank-child-host.mjs:1-8` 已记录同一现象：
onnxruntime-node 在进程内被强杀会带走整进程）。⇒ 撤销该方向：`MemoryReranker` 不再有 `cancelPending`，
被放弃的那一块自然跑完即弃，代价上限是「一块（≤4 条）的延迟记到下一题头上」，与整进程崩溃不可比。
`warmup` 保留。

**决定 21（调用方放弃 ≠ provider 故障）**。`ranked === null` 时不再一律 `breaker.recordFailure()`：
`softTimedOut` 只记 debug 日志。否则「3 次预算到点」就被记成 provider 三连失败 → 熔断 open →
后续题全部跳过精排（armR4 的 61/90 就是这样废掉的）。真实 provider 故障仍照旧推熔断。

**被否决的形态（都是实测，不是推断）**：`chunk=6 / budget=700ms` 只做块间检查 → 精排 p95 1390ms、
max 1910ms；`chunk=3 / budget=300ms` → p95 **1557ms**（块越碎、慢块的暴露面越大）；`warmup 后不设预算`
（=原行为）→ p95 1072ms；`软超时即 terminate worker` → exit 127。
