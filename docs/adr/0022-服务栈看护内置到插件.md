# ADR-0022 服务栈看护内置到插件：外部 bundle `tdb-lifecycle` + PowerShell 看护进程退场

- **状态**：已接受（2026-11-01，来源：用户令「那这个为什么不内置到插件中，你改一下吧，改成插件内置」；实施票 = Wave 4，代码见 `dsh-plugin/src/services/**` 与 `dsh-plugin/client/client.js`）
- **关联**：ADR-0020（MemoryProxy 退场——本条废掉了唯一还记得 proxy 的进程）、ADR-0021（可选后端退场——三服务现在只有 sqlite/local 一套配置）；实现面 `dsh-plugin/src/services/{supervisor,service-table,health,control,install,env-file}.ts`、`dsh-plugin/src/{config,config-schema,index,types}.ts`、`dsh-plugin/client/client.js`
- **域词典**：[CONTEXT.md](../../CONTEXT.md) → 服务栈 / 看护进程 / 健康门 / owned
- **取代**：外部 bundle `D:\TDB\integrations\dsh-tdb-lifecycle`（`link:` 依赖，383 行 `lib/index.js` + 320 行 `lib/client.js`）与 `D:\TDB\etc\start-tdb-supervised.ps1`（PowerShell 看护进程）

## 背景（2026-11-01 事故取证）

Wave 3 把服务表从四服务改成三服务（删 proxy 8096）后，磁盘上的 `D:\TDB\etc\tdb-services.common.ps1` 是对的，
但**正在跑的看护进程用的是自己内存里的旧表**：

```
$ curl -s http://127.0.0.1:8444/status | …
supervisor {running:true, pid:41120, startedAt 15:17:37, tetheredToThisHost:true}
services: tdai-core 8420 pid 21176 owned
          tdai-proxy 8096 pid 22376 owned      ← 已从表里删掉的服务，仍然 owned
          tdai-knowledge 8421 healthy pid:null owned:false
          tdai-panel 8123 pid 27700 owned
$ cat D:\TDB\data\run\tdb-supervisor.state.json → owned.tdai-proxy = 22376
```

后果是三重的：

1. **服务表有两个真源**：磁盘一份（三服务），看护进程内存一份（四服务）。改了磁盘不等于改了运行态，
   必须重启宿主（`taskkill` 整树 + 新 host 重拉）才生效——而重启宿主的成本是打断用户当前会话。
2. **死进程拉活**：我先 kill 了 22376，看护进程 2s 轮询发现它死了，按预算又把它拉回来。
3. **`MemoryProxy/` 目录删不掉**：22376 的 cwd 在那个已清空的目录里，Windows 不允许移除被占用的目录
   （`rm -rf MemoryProxy` → `Device or resource busy`）。于是「代码里已经没有 proxy 了」和「磁盘上还挂着一个 proxy 进程」同时成立。

同一次排查还发现外部 bundle 自己也带了第三份表：`lib/index.js:50-53` 硬编码 `SERVICES`（含 `tdai-proxy 8096`）、
README 通篇 four-service、`package.json` description 也写 four-service。三份表分布在 PowerShell、bundle 的 JS、配置文件里，
任何一处漏改都会在下一次重启时复活。

## 决定

1. **服务栈的生命周期归插件**。`dsh-plugin` 自己在 `apply()` 里拉起并看护 `tdai-core`(8420) / `tdai-knowledge`(8421) / `tdai-panel`(8123)，
   服务表只有一处真源：`src/services/service-table.ts` 的 `defaultServiceTable()`（端口可被 `services.*` 覆盖）。
   外部 bundle 与 PowerShell 看护进程整条退役。
2. **缺省关，部署方显式打开**（`services.enabled: false`）。装/升级插件不该顺带起三个 node 进程；
   本机在 desktop patch 里显式 `services: { enabled: true }`。这与「谁启动服务栈是部署决定」的既有口径一致。
3. **健康门语义照抄旧看护进程，不发明新的**：按表顺序启动；已健康的跳过且**不记 owned**（别人的进程不碰）；
   spawn 后等 `/health` 200，预算 `healthTimeoutMs`（缺省 90000，core 冷启要跑 jieba/embedding 预热）；
   超时即 kill、记 `failed[]`、抛 `'<name> did not answer /health on port … within Xms (attempts=N); see <logDir>'`（abort start order）。
4. **状态文件换名**（`<runDir>/tdb-services.state.json`，旧的是 `tdb-supervisor.state.json`）：
   旧看护进程可能还活着并在写同一个文件，共用一个文件会让 adopt/reap 判断互相污染。
   状态里存 `hostPid` 与 `owned{name:pid}`，语义三条：
   - `hostPid` 活着且不是自己 ⇒ **adopt**（不 spawn，避免两个 DSH 窗口抢端口）；
   - `hostPid` 已死 ⇒ 先 `reapOrphans()` 杀掉上次的孤儿；
   - `stopOnDispose: false` ⇒ **detach**（状态写 `hostPid: 0`、`owned: {}` 后走人，下次不回收也不 kill）。
   **主动 kill 的 pid 必须进 `suppressed` 集合并从 exit 回调里摘掉**——否则健康门失败后的 kill 会被看门狗当成崩溃、立刻重拉，
   形成「拉起来→健康门失败→杀掉→再拉起」的死循环（这是 Wave 4 实现期真踩到的 bug，测试先红后绿）。
5. **环境变量只认一个文件**（`services.envFile`，缺省 `D:/TDB/etc/services.env`，KEY=VALUE + `${VAR}`）：
   插件与手工 PowerShell 两条启动路径读同一份值。`D:/TDB/etc/env.ps1` 改写成「dot-source 这份文件再导出」的加载器，
   12 个变量 sha256 逐项比对一致后才删旧逻辑（备份 `D:\TDB\data\retired\2026-11-01\env.ps1.bak-wave4`）。
   每次 spawn 重读文件（换 key 下次重启即生效）；展开失败**只报变量名，绝不回显值**。
6. **控制面保持兼容**：端口仍 8444、路径仍 `/tdb-lifecycle/*`、POST 仍需 `X-Tdb-Control: 1`。
   这样旧书签、旧同源路由、以及用户对「TDB 服务」这块位置的肌肉记忆都不用改。
7. **fail-open**：`supervisor.start()` 抛错只 warn，绝不让插件挂载失败。拉不起服务栈时插件退化成「直连一个已经在跑（或不在跑）的 core」，
   与 `enabled: false` 的行为等价。
8. **设置页那块不依赖配置表单可用**：服务面板故意 inject 在 `configForms.whileServed` 之外——
   表单挂掉（Host 没给 profile entry）时仍要看得到服务死活。

## 后果

- 一个东西要修的地方从「PowerShell 表 + bundle 常量 + README + package.json」变成「一个 TS 数组 + 一份 yaml 模板」。
- 服务起停的观测面从 `curl 8444/status`（外部进程）变成同一端口同一形状，但数据直接来自插件内存（`status()` 现算 pid 存活与 `/health`），
  不再有「state.json 说 owned 但进程早死了」的窗口。
- 宿主退出时默认连带停服务（`stopOnDispose: true`）；要「让栈活下去」必须显式 detach，且**会留痕**（`hostPid: 0`），
  下次启动既不 adopt 也不 reap——三种意图（我拥有 / 别人拥有 / 没人拥有）在状态文件里可区分。
- 依赖方向是单向的：插件 import core 的**端口号约定**（8420/8421/8123）与 `/health` 形状，不 import core 的代码。
  core 改端口只需改配置（`services.*` 覆盖），不需要改插件源码。
- 诚实边界：插件自己不再是「纯客户端」。它现在会 spawn 子进程、写日志目录、绑 8444 端口。对「插件只发 HTTP 请求」这个印象而言这是行为扩张，
  代价换来的是单一真源与可观测性；不想要就 `enabled: false`，此时行为与 Wave 3 完全一致。

## 观测锚

| 锚 | 位置 | 期望 |
| --- | --- | --- |
| 状态文件 | `<runDir>/tdb-services.state.json` | 只在插件拉起过服务时存在；`hostPid` 是**宿主** pid |
| 控制面 | `GET http://127.0.0.1:8444/status` | `supervisor.running` + 三服务表，**不再出现 `tdai-proxy`** |
| 日志 | `GET /health` 失败时的错误串带 `see <logDir>` | 每服务每代一份 `<name>-<stamp>.{out,err}.log` |
| 设置页 | 设置 → TDB 记忆 → TDB 服务 | 服务表 + 启动/停止 + 单服务 restart |
| 旧进程 | `tasklist \| findstr pwsh` 应无 `start-tdb-supervised.ps1` | 重启宿主后旧看护进程不再出现 |
