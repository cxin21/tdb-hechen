# ADR-0025 L1 属性四档收口：溯源落库、零读列退场、敏感度改当注入门

- **状态**：已接受（2026-11-04；来源：用户令「结合代码分析 L1 记忆的属性，哪些必要、哪些非必要、哪些需补充，注意和主流记忆系统与人格系统对比分析」+ 后续拍板「冗余若无用且提升不了系统能力就删，否则好好设计」「所有属性必须有使用的地方不能空挂」「必须落到可推广的生产级，不能有遗留」）
- **关联**：取证报告 `docs/research/2026-11-04-l1-attribute-audit.md`（§3 四档、§5/§6 主流与人格对标、§10 施工定案与版本化勘误）；ADR-0010（双时态与软失效）、ADR-0015（事实级一行一事实）、ADR-0016（受控属性词表）、ADR-0023（分层与提取七项）、ADR-0024（召回标准档）
- **域词典**：`CONTEXT.md` → 灵魂六属性、价值锚、严格规则、身份槽

## 背景

记忆系统（Letta / Zep-Graphiti / Mem0 / A-MEM / Generative Agents）与人设格式（Character Card V2）的字段清单对齐后，本仓 L1 行有 22 个物理列 + 一张关系表，但**字段存在 ≠ 字段在用**。实测 4225 行生产数据：

- 有 6 项属性既无读点也无有效产出（`source` 零读取、`timestamp_start` 与 `timestamp_str` 4225/4225 逐位相等、`task_id` 100% 空、`metadata.importance_reason`/`created_by` 零判定读点、`metadata.evolution` 0 行）；
- 有 8 项「写满、读点被 0 掐断」（TODO：见报告 §3-B）；
- 主流系统都有而本仓**缺**的硬字段是**行级溯源**：`MemoryRecord.source_message_ids` 与抽取 prompt 都要求它，DDL 却没有列，读回硬编码空数组（`store/l1-reader.ts:80` 注释 "not stored in SQLite"）——**记忆不可回指原话**，与 ADR-0003「有解释功能」「真实用户文件零接触」的证据链要求冲突。

## 决定

1. **行级溯源落库（D1，已完成）**：`l1_records.source_message_ids TEXT NOT NULL DEFAULT '[]'`（`core/store/sqlite.ts:787-789` + `:819-821` 幂等 ALTER）。写入透传、`archive`/`restore` 保全、`getL1ByIds` 与三条编辑重建链（`/atomic/update`、`/atomic/importance`、`/atomic/invalidate`）全部携带——**编辑记忆不得清空证据**。
2. **零读列退场，不留「停写但列还在」的空挂态**：`source` 删列（信息由 `source_message_ids` 非空 + `memory_audit` 承担）；`timestamp_start` 删列 + 删两条死索引（投影改取 `timestamp_str`，**对外 `created_at` 的值逐位不变**）；`metadata.importance_reason` 与 `metadata.created_by` 删写入；`metadata.sensitivity` 键收敛到列。
3. **`task_id`：写读链本来就通，缺的是生产者（2026-11-04 二次取证勘误）**——原判「隔离轴只接读没接写」**不成立**。逐跳实测：`iso.taskId` → `gateway/v2-router.ts:1080` L0Record.taskId → `store/sqlite.ts:5071` upsertL0 落 `l0.task_id` → `queryL0GroupedBySessionId:5718`（groupKey 含 taskId）→ `pipeline-factory.ts:810` → `l1-extractor.ts:606/622/626` → `l1-writer.ts:321` → `sqlite.ts:1800` upsertL1，全通；读侧五处过滤（`sqlite.ts:4922/5007/5415/5833/5896`、`v2-router.ts:1278/1324/1806`）与面板展示（`MemoryPanel/web/src/pages/ChatMemoryPage/components/block-detail/AttributesSection.tsx:160`）也都在。生产 14100 条 L0 / 4225 条 L1 的 `task_id` 全空，唯一原因是**上游生产者（TDAI MemoryProxy 的 preset/task 头）在 DSH 特化波次被整条删除**，本仓唯一客户端 `dsh-plugin` 从不发 `iso.taskId`。交付形态：**不删列**（对外契约 `iso.taskId` 仍被接受，删列=API 面变更），补往返/收窄测试证明该轴可用 + 文档写明「可选业务维度，缺省=不限」；「整轴退场」的方案与爆炸半径见取证报告 §10.6——**本轮按 A 方案收口（保留契约 + 补往返/收窄测试 + 文档写明可选语义）**；B 方案留档，仅在明确需要「隔离模型回归四维」时执行。
4. **`sensitivity` 的语义从「降分」改为「不外泄/不注入」（已落地，形态见下）**：写侧照旧标注；读侧是**注入门**——非 `none` 行只在可证明的私有上下文注入，其余一律不注入且必须可观测计数。撤销两个恒 0 的排序/遗忘乘子（`recall-signals.ts` 的 `sensitivityMultiplierOf`、`forgetting/scorer.ts` 的 `sensitivityBias`），保留注入行「敏感:…」徽章。
   **可见性判定不新增请求字段，而由「候选池归属」推导**（`recall/sensitivity-policy.ts:251` `audienceOfOwnerScope`）：池按 `user_id` 收窄且该 `user_id` **不等于** `DEFAULT_ISOLATION_ID`（`store/isolation.ts:13` 的 `default` 是多主机共用兜底桶）⇒ `{chat:"direct", sharing:"private"}`；其余（无 `userId`、空白、`default` 桶）⇒ `undeclared`，**fail-closed**。理由：`RecallRequest`（`gateway/types.ts:59-63`）只有 `query/session_key/user_id`，`l0_conversations` 无会话类型列，`session_key` 是 `dsh-plugin` 透传的不透明 id，全仓无任何可持久化的群聊信号——因此**不预留 `audience` 配置键**（无生产者=空挂），也**不把 `default` 桶当私有**。将来接入群聊面时由边界显式声明 `group/shared`，`resolveAudience` 的 deny 优先会压过 `private`。
   两个注入点各调一次**同一谓词**：钩子路注入块（`hooks/auto-recall.ts:4639-4675`，计 `gates.sensitivity`）与工具路 `memory_search` 返回（`tools/memory-search.ts:1874` `gateSensitivityForInjection`，两条 trim 早退/双路分支 :1236 / :1715，计 `result.sensitivity`）——工具返回同样进模型上下文，属同一可见内容面。观测口径：`scanned`（池里带标注行数，含 `unclassified`；**0 不等于门没生效**）/`blocked`/`byReason`（只出非 0 项）/`audience`；`scanned=0` 时整块缺省，不塞噪声。枚举外脏值按 `unclassified` 拦（`recall/sensitivity-policy.ts:164` `decideSensitivityInjection`）。
   **两条链的可见性来源必须都是服务端可证的租户三元组，不能是模型/提示词声明**：钩子链 `performAutoRecall`（`hooks/auto-recall.ts:533-560`）显式接受并透传 `isolationFilter?`（此前只靠 `{ ...params }` 生效，是"能跑但不在接口上"的暗开关）；程序式调用不传 ⇒ 旧行为逐位、敏感行 fail-closed；`tdai-core.handleBeforeRecall(query, session, isolation?)` 与 legacy HTTP 路由 `gateway/server.ts:1752-1775` 读 `x-tdai-{team,user,agent}-id`（与 `/capture` 同口径）后透传；生产 `dsh-plugin` 走 `/v3/recall` 恒带三元组头 ⇒ 判为 `private`，本人私有上下文里健康/财务记忆照常可用。
5. **soft 效期档定案「修」而非「撤」**：`selectByValidity` 的 `kept` 顺序是 soft 语义的唯一表达；钩子路必须用 `applyKeptOrder`（`recall/validity-policy.ts:237-243`）按 kept 重排，禁止「只用 kept 做集合判断、顺序从原数组重算」。journal 增 `demoted` 计数，替代恒为 0 的 `dropped`（soft 只数 future）。
6. **`certainty` 保持二值、暂不数值化**：它的价值在 8 个「非排序门」（L2 排除 inferred、巩固洗白、遗忘跳过、演化双 observed、reconsolidation 白名单、`recall_count` 只对 observed 累加），排序侧已降为平局旗标。升 `confidence REAL` 须等召回优化线收口后另行评估，本 ADR 不新增字段。
7. **「按配置关断的能力」不按空挂处理，不删**：`timeBoost`/`recencyBoost`/`sigWeight`/`moodBoost`/`sceneBoost`/`emotionSalienceWeight`/`graphDiscount` 全为 0，但它们各有读点与 golden 测试，属「能力保留可重开」。删它们=销毁回归证据，与「不要留悬空开关」不是同一件事：**悬空=无读点无证据；关断=有读点有 A/B 记录**。PPR 通道重开前置见 `tdai-gateway.yaml:210`。
8. **人格层补两个对流缺口（已落地）**：
   - **人设版本三件套**：`soul_snapshots` 增 `version`/`parent_hash`/`reason_detail`/`slots_json` 四列（`store/sqlite.ts:937` + `:973-976` 幂等迁移，旧行 `version=0`）；`writeSoulSnapshot`（`:2829`）在 `BEGIN IMMEDIATE` 内比对上一版 `content_hash`，**同内容零落行**（幂等不刷版本号），否则 `version=max+1`、`parent_hash=上一版 hash`；`trigger` 的自由文本 `"render"` 升级为受控闭集 `first-version|identity-discovery|core-values|promise|state|slots|layout` + 自由 `reason_detail`（`hooks/soul-versioning.ts:13` `SOUL_CHANGE_REASONS`、`:166` `classifySoulChange`），键级 diff 存 `slots_json`（`slot:`/`value:`/`block:` 三键空间，`:83`/`:119`）；两处写入点收敛到 `recordSoulSnapshot`（`hooks/soul-assembler.ts:297`，调用点 `:448`/`:991`）；`soul-introspect.ts:102-115` 仅在新列存在时补字段，老行不冒充受控 reason。
   - **L2 场景块触发词**：META 可选第五行 `keywords: k1, k2`（`scene/scene-format.ts:74-81`，无该行的旧块**逐位等于旧格式**），索引透传（`scene/scene-index.ts:70-79/129-136`）；抽取 prompt 只在结构化形态要求「3-8 个中文原词短语、必须取自对话原文」（`scene/scene-structured.ts:490-492`），蒸馏 prompt 要求原样保留（`scene/scene-governance.ts:53/77`）；注入侧 `recall-layered.ts:253-286` 命中即**越过** `sceneHit/textHit` 与 `minUniqRatio` 密度门（显式意图优先于启发式补位，Lead 2026-11-04 定案），`:312-343` 预算预留（无可让位则诚实降级、绝不超预算），未命中路径 `keptFlags` 与旧路径逐位相同；观测面 = 返回值 `keywordTriggered` + debug 日志 + journal `layeredKeywords`（`recall/recall-journal.ts:420`，同一份计数三条留痕同源，缺字段=无命中）；`scene_block` 的 identity 门仍在触发判定之前（含人设回显的块即使命中也不注入，有意保留）。

9. **`updated_at` 双语义拆分（第二批 B 项，已落地）**：`l1_records.updated_time`（行最近被写的时间）与 `l1_records.timestamp_end`（**事件结束时刻**）此前在两条读路上各自冒充 `updated_at`——`/v3/atomic/query` 取 `updated_time`（`gateway/atomic-query-fields.ts` `handleAtomicQueryShape`），`memory_search` 行映射取 `timestamp_end`（`core/tools/memory-search.ts` 七处行映射）。同一个字段名两种语义 = 客户端无法自证时间基线，且「最近更新」在工具路读成「事件结束」。
   **定案**：`updated_at` 统一指 `updated_time`（行更新时间，取不到时回退 `timestamp_end` 保持旧库可读）；新增 `event_end_at` = `timestamp_end`，语义显式；`timestamp_end` 列**保留**（时间线与效期计算仍用它）；面板属性区并列展示「最近更新」与「事件结束」两行，时间线仍用 `timestamps`。**不加配置开关**（双语义是缺陷不是选项）；`/v3` 只新增字段不改既有字段名 ⇒ 老客户端零影响。
   **空串按未写处理**（第二批复核补正）：`l1_records.updated_time` 的 DDL 是 `TEXT DEFAULT ''`，`??` 会把空串当有效值直接吐出去（`updated_at: ""` 比任何时间都糟），故七处行映射 + 两个 shape 统一按「空串 = 未写」回退 `timestamp_end`；归档回退路本来就用 `||`，口径就此统一。
10. **显式降敏：给「单向棘轮」补下限（第二批 A 项，已落地）**：`sensitivity` 的语义是注入门（决定 4），但写侧 `inheritSensitivity`（`core/record/l1-writer.ts:263`）只升不降、`upsertL1` 的 `sensitivity` 是**粘性列**（`core/store/sqlite.ts` 的 `CASE` 把 `none`/空/NULL 当「本次未判定」保留旧值）——两条自动路径叠加的结果是**误标后永远降不回来**，且没有任何人工出口。
   形态：① store 新增 `setL1Sensitivity(recordId, value, expect)`（唯一降敏写路，单条 `UPDATE … WHERE record_id = ? AND COALESCE(sensitivity,'none') = ?`，绕开粘性 `CASE`，主表 + `l1_fts` 双写，只 bump `updated_time`、**不 bump version、不改正文**）；② `POST /v3/atomic/sensitivity`（`gateway/v2-router.ts` `handleAtomicSensitivity`）——白名单 `none|health|finance|relationship`、**`expect` 为必填 CAS 条件**（不带=盲覆盖→400）、`changes=0`→**409**、无行 404、跨租户三轴 403、后端未实现该方法→**501 fail-loud**（不静默成功）；③ 审计 `memory_audit.action='sensitivity'`（与 update/delete 同等留痕）——**库级 CHECK 枚举必须一起迁移**：老库 `CHECK (action IN ('update','delete'))` 会把新 action 写成异常并被 `recordAudit` 的 catch 吞掉，等于「降敏成功、审计静默丢失」，故 `migrateMemoryAuditActionEnum()` 幂等重建 `memory_audit`（`CREATE new + INSERT SELECT + DROP + RENAME`，判据=DDL 含 `'sensitivity'`）；④ 面板 `AttributesSection` 加 owner-only「解除敏感标记」（二次确认，回传 `expect=当前值`），BFF `MemoryPanel/src/panel/http/routes/chat-memory.ts` 透传。
   **方向约束放 UI 不放网关**：网关保留通用写能力（`health→finance` 这类重分类将来可能需要），保守语义（只允许「降为 none」）由面板按钮表达。**同时修掉的邻接缺陷**：`/v3/atomic/importance` 的 handler 早已在 `DATAPLANE_HANDLERS` 注册，但封闭清单 `V3_ALLOWED_SUBPATHS` 一直漏登 ⇒ 该端点线上恒 404、面板调级不可用——本项核对新端点时发现并补登（分发级用例同时钉住「新端点可达」「补登生效」「清单未放开」三条）。
11. **边型（`l1_links.type`）收成受控词表（第二批 D 项，已落地）**：此前边型是散落字面量——六个写点各写各的字符串，`addLink`/`getLinksByType` 的参数是裸 `type: string`，`pprKindRank` 还特判一个**不存在于任何写点**的 `causal`。定案：`core/store/types.ts` 建 `LINK_TYPES`（`derived_from`/`similar`/`part_of`/`conflict`/`evolve`/`evolved_from`）+ `LinkType` + `LINK_TYPE_VALUES`，五个写点（`record/l1-extractor.ts:1418/1420/1423/1464/1558`、`lifecycle/consolidation/consolidation-worker.ts:538`、`lifecycle/reflection.ts:137`、`lifecycle/evolution-worker.ts:297/298`、`utils/pipeline-factory.ts:1275`）与两处读点（`evolution-worker.ts:164/168`）改用常量，接口参数类型收窄为 `LinkType`；`pprKindRank`（`recall/ppr.ts:62`）按真实词表重排 `evolved_from=0 / conflict=1 / 其余=2`，删除 `causal`、`evolve` 特判。
   **存量口径**：生产 `D:/TDB/data/vectors.db` 实测 54953 条 `l1_links` 的 distinct type 全部落在六值内（`derived_from` 42967 / `similar` 9939 / `part_of` 1226 / `evolve` 730 / `conflict` 91），`causal` 零行 ⇒ **零越界、无需迁移回填**（`evolved_from` 生产 0 行属预期：只在演化 worker 合并时写）。`pprKindRank` 重排的数值影响为零：55057 个 `(source_id,target_id)` 对中带多种 kind 的对 = 0，邻接表排序键不会重排 ⇒ PPR 求和顺序与 `pprNorm` 逐位不变；唯一行为变更是并列时的主导边类型标签（旧 `evolve` 优先 → 新 `conflict` 优先，只影响 `recall_channel` 里的标签字符串）。面板侧调色板与图例同步对齐六值（`MemoryGraphView.tsx` `EDGE_KIND_COLOR`、`RelatedSection.tsx` `EDGE_CLS` + 图例、`chat-memory-panel.css` 的 `--mem-sem-*` 与 `._nb-edge--*`）：`derived_from` 与 `evolved_from` 此前恒灰、`causal` 是死色。§ 测试：词表用例直接读源文件做字面量扫描（五写点散落 `'similar'` 等必须为空 + 每文件引用计数钉死，防「正则失效 → 空集 ⊆ 全集」永真）。

12. **注入面的字段完整性是门的一部分（对抗评审 P0/P1 修复，已落地）**：门的判据是「行上有没有 `sensitivity`」，所以**任何一条召回路径少投影这一列，等于给该路开了一个静默旁路**。评审实测 `memory-search.ts` 的 FTS / native-hybrid / 图扩展 / neighbor 四条腿都只投影了部分灵魂列、唯独漏 `sensitivity`（向量腿有），而 `classifySensitivity` 对 `undefined` 返回 `none`（= 放行）；再叠加 RRF 合并只并分数不并字段、混合路 `ftsItems` 排第一 —— **同一条敏感行只要被 FTS 与向量同时命中，胜出的就是那个没有 `sensitivity` 的对象**，门判 `none` 放行；无 embedding 的降级场景 100% 走 FTS 腿。定案三条：
   - **投影完整性**：四条腿全部补 `sensitivity`（`tools/memory-search.ts` 的 fts/hybrid/graph/neighbor 分支），并在 `rrfMergeWeighted` 里补一条字段合并规则（`existing.item.sensitivity === undefined && item.sensitivity !== undefined` 时取后者）——分数合并的语义不变，只保字段。
   - **失败语义二分**：`setL1Sensitivity` 的两条 UPDATE 放进同一事务（`BEGIN IMMEDIATE`），CAS 未命中 → `ROLLBACK` + `false`（409）；底层异常/degraded → `ROLLBACK` 后 **throw**（503）。此前异常也返回 `false`，网关一律回「CAS 未命中」，客户端按并发冲突重试永远失败、且审计无行。
   - **两条对外路同输入面**：工具路此前不透传归属、也不回观测 —— `MemorySearchParams.isolationFilter` 新增并透传到 `executeMemorySearch` 的 `filter`（注意选项名是 `filter`，不是 `isolationFilter`），legacy `/search/memories` 读 `x-tdai-{team,user,agent}-id`，返回带可选 `sensitivity` 观测（`blocked>0` 时宿主可提示「有内容被过滤」）。
   - **门在生产截断之前**：`slice(0, limit)` 之后过门会让敏感行白吃名额，返回条数无故小于 `limit`、`total` 缩水且无提示；两条分支统一改为「先门、后截断」。
   - 边界（不改）：`recordAudit` 仍是 best-effort（审计失败只 warn，不影响用户写操作）——安全动作的审计完整性依赖库已迁移到新 CHECK 枚举，迁移前 `action='sensitivity'` 会被库级 CHECK 拒绝并丢弃；本机生产库的迁移在下次 store init 时执行。

13. **属性生命周期契约：「只在 UI 出现」不算使用（第三批，已落地）**：用户定案「没有使用不仅是指 panel UI 没有使用；仅在 UI 使用而没有参与记忆捕获、提取、召回、灵魂提取、注入等等的也算没有使用」，并把「使用」定义为**非展示代码路径读取该属性并改变行为**（UI/API 出参不计）。
   形态：`core/attribute-contract.ts` 建 `ATTRIBUTE_CONTRACT` 注册表（16 条：9 个 soul 列 + 7 个基础列），每条登记 `storage` / `stages` / 非 UI 消费点 `{path, symbol, effect, stage}` / UI 面 / 定案备注；`core/__tests__/attribute-contract.test.ts` 逐条核验真实源码里符号存在（删读点即红）、每条 ≥1 个非 UI 消费点（仅 UI → 红）、每条有 UI 可见面、soul 列全覆盖且无幽灵字段。这是把「属性有没有用」从一次性人工结论变成构建期契约。
   五项落地：
   - **`source_message_ids` 从「只写不读」变成提取期证据主键**：抽取时与当批 messages 的 id 求交（剔除模型幻觉 id，计数 warn）；`store.findL1BySourceMessageIds(ids, filter?)` 按来源反查既有记录；若某条既有记录**完全覆盖**新记忆的来源 id，dedup 决策由 `store` 覆盖为 `update`（`target_ids=[既有记录]`）——同一批原话不再重复落一行，且不做 `skip`（保留内容改进）。
   - **`importance` 统一进 worthiness**：遗忘打分新增 retention 乘子 `factor = clamp(1 + k·(imp−5.5)/4.5, 1−k, 1+k)`（`k=forgetting.importanceRetention`，缺省 0.2；`imp` 缺失=NULL → factor=1 中性，不罚未评分行）——此前 `scoreFor` 完全不读 importance，低重要度记忆与高重要度同寿；同时把工具路 `memory_search` 的 `importancePenalty` 参数化（`tools/memory-search.ts` 新增入参，`gateway/v2-router.ts` 与 `core/tdai-core.ts` 从 `memory.recall.importancePenalty` 透传），删掉「工具路硬编码 DEFAULT(0)、hook 按配置开启」的双口径。
   - **`task_id` 补上生产者与采集端**（决策 3 的闭环；采集端 = `dsh-plugin` 会话开始的第三问，与 team/agent 同级）：`gateway/server.ts` 的 `/capture` 读 `x-tdai-task-id` → `handleTurnCommitted` → `performAutoCapture` → `l0-recorder` 落 `l0_messages.task_id` → 既有 `group.taskId` 链 → `l1_records.task_id`；`/recall` 与 `/search/memories` 同头参与作用域过滤。仍保持「可选业务维度，缺省=不限」。弹窗侧对齐 DSH 特化前的 proxy（其 `FormStage` 五态含 `task_select`，`MemoryProxy/src/session/dsh/form.ts` 于特化 Wave 2 随包删除）：`dsh-plugin` 的会话开始卡片在 team → agent 之后追加 Task 一问，选项 = proxy 同款的虚拟默认项「本次不关联任务」（恒在首位）+ 该 team 的 running 工作项（`/v3/meta/task/list`，`status: running`，label = `title (task_id 后 8 位)`）；只有选中真实任务才发 `x-tdai-task-id`，选默认项/跳过 = 该轴留空且**不影响** team/agent 绑定；开关 `identity.askForTask`（缺省开）。
   - **面板 P0 修正**：敏感度 chip 正文从字面量 `x` 改为真实标签（`SoulSection.tsx:96`）；「复制 JSON」补 `sensitivity`/`task_id` 原始键（`AttributesSection.tsx:336-346`）；importance 调级与失效/恢复表单统一 owner 门（`AttributesSection.tsx:443`）；soft 模式「已失效」tooltip 不再声称「两路召回均排除」（实际是降权保留，`utils/attribute-badges.ts:75-94`）。
   - **面板 P2 修正（后端早已能用、前端不用）**：① 邻接属性摘要——内核 `v2-router.ts:2501-2509` 一直返回 `occurred_at/valid_start/valid_end/certainty/valence/arousal/significance`，而 `RelatedSection` 只声明并渲染 `type/content/strength`，属性被整段丢弃；现抽成纯模块 `block-detail/neighbor-attrs.ts`（`Neighbor` 类型 + `neighborAttrChips`，顺序=显著性→确定性→有效期→事件时刻，无值不占位），组件按 `_nb-attrs` chips 渲染（`RelatedSection.tsx` 邻居行），过期只写「已过期」不写「已删除」（与 soft 语义一致）；api 出参类型同步补 `valid_start/valid_end/arousal`（`web/src/lib/api/chat-memory.ts`）。② type 过滤接线——BFF `:3151-3152` 与 web api `searchLayer(..., type?)` 早已支持，UI 从不传；现 `BlockDetail` 在 L1 搜索区加类型选择器（全部/episodic/work_fact/instruction/persona/work_method/work_task），`onSearchLayer(l, q, type?)` → `useChatMemory.searchLayer` → api，L0 恒不传；锁在 `MemoryPanel/tests/related-neighbor-attrs.test.ts`（8 例：chips 规则 + 接线源码断言）。
    - **边界（已补）**：注入链 `auto-recall.ts:5198` 与工具路 `tools/memory-search.ts:1867` 曾把 `significance` 渲染成「重要度／重要」（与 importance 撞名）；2026-11-04 晚改渲染为「显著性」（`auto-recall.ts:5192-5199` 注释钉住「重要度=importance 1-10 专名、显著性=significance 0-1 连续值」），复跑 `src/core/hooks`+`src/core/tools` 106 files / 1074 tests 全绿。译名只影响渲染文本，机读字段名不变。

14. **加权通道按 A/B 重开（第三批后追加，已落地 2026-11-04）**：significance / valence / 情绪显著性三路在 #145 收尾时被判「无实测作用」而钉 0；本轮按用户令重做同库 A/B（longmemeval_oracle 90 题 / 2725 轮，新建沙箱库，--store + --no-write-steps 复用，--gen-limit 0 只测检索）后按 0.03 / 0.03 / 0.05 开启：
    - 结果：combo 组（n=5）vs 全 0 组（n=3）——session_cov 96.56±0.18 vs 95.78±0.40（+0.78pp）、turn_cov 88.05±0.85 vs 87.15±0.85（+0.90pp）、MRR 0.6996 vs 0.7029（−0.0033）、nDCG 0.6940 vs 0.6916；**全部落在重复噪声内**（同配置 5 次重跑 turn_cov 85.6%–90.8%，σ≈1.9pp），强度标记 **ns**。
    - 幅值不敏感：0.01 与 0.03 的 sigWeight 位移几乎相同（turn 86.7 vs 86.6、MRR 0.698 vs 0.700）——两路信号作用在 rrfScore 1e-2 量级的微差/平局处，不是连续调权，因此**没有「调小即无害」的中间档**。

## 后果

- 注入面（决定 12）：门的有效性不再依赖「每条召回路径恰好都记得投影敏感列」——四条腿 + RRF 合并 + 端到端用例（FTS 单腿 / 两腿同 id 合并 / 图扩展腿 / 私有归属放行 / 门在截断前）共同钉住；`blocked>0` 时对外有观测，不再静默少内容。
- 读侧 API 面：`created_at` 值不变但列来源改为 `timestamp_str`；`source_message_ids` 成为 `L1SearchResult` 的可选字段（老客户端忽略即可）；删列走迁移，老库自动补/删，存量行读回不抛。
- 写入面：编辑/重要度/失效三条路径都会带上溯源，行内容改写不再抹掉证据链；且 `task_id` 与 `source_message_ids` 是**粘性列**——`ON CONFLICT` 用 `COALESCE(NULLIF(excluded.…,''), …)`（`sqlite.ts:1107` L1 / `:1126` / `:1254` L0），本次 upsert 没带即保留旧值（「没带」与「清空」不可区分，一律按没带），显式新值照常覆盖。
- 排序面：normalized 档的 `relevance` 归一改为 **降权前分母**（`tools/memory-search.ts:792-822` 第 6 参 `relevanceScalePreSoft`，钩子路 `auto-recall.ts:4503-4523`/`:4570-4576` 采集；`compositeScoreOf:764-767` 加 `Math.min(1,…)` 上界钳制）——旧实现把 soft 降权后的分数当分子、池内最大值当分母，降权反而**升权**；生产 `rerankWeights` 全 0 时无差异，属潜在缺陷修正。
- **不做**：不补 `importance` NULL 的默认值（987 行 NULL 中 961 是生命周期卡，NULL=未评分≠低分）；不把 `actor` 交给 LLM 推断（`l0_conversations.role` 已有确定值）；不在 normalized 融合档盲目加 recency 权重（历史 A/B 零差异）；不删 `metadata.importance_source`（manual/llm 是 /atomic/update 唯一防篡改痕迹）。
- `task_id` 保持五轴之一（B 档保留）：生产填充率 0 是**调用侧事实**，不是断链。本轮定案 A（不删列）：删列属 /v3 契约面变更而收益仅为「少一个空维度」，代价不对称；B 的逐项清单留在报告 §10.6。
- 时间面（决定 9）：`updated_at` 二值一名的歧义已消除——工具路行映射与 `/v3/atomic/*` 现在同口径（行更新时间），事件结束改由 `event_end_at` 显式承载；`timestamp_end` 列未删（时间线/效期仍读它），因此**不是**第二次「停写但列还在」的空挂态。
- 敏感度面（决定 10）：人工降敏成为唯一「只降不升」写路，自动路径仍 fail-closed 只升；面板以 owner-only + 二次确认 + CAS 表达，误标可纠正且留痕。
- 关系面（决定 11）：边型从「写字面量的默契」变成编译期可查的受控词表；`LinkType` 收窄后新增边型必须先进词表，否则类型门直接红——这是把「静默漂移」换成「构建期失败」。`pprKindRank` 的语义理由（`evolved_from` = 同一事实的新旧链、`conflict` = 矛盾双方都留）已写进函数注释，不再依赖历史特判。
- 属性面（决定 13）：16 条属性各自有可核验的非 UI 消费点，其中 3 条从「写了没人读 / 只在一条路上生效 / 缺生产者」变成真实生效（`source_message_ids` 参与判重、`importance` 参与归档与两条召回路、`task_id` 有生产者）；`core/attribute-contract.ts` + 测试把这条结论固化为每次构建的硬门，后续新增属性漏登记会直接红。
- 遗留（另行排期，不在本 ADR 落地范围）：`confidence` 数值化、实体主键最小版（`entity` + `l1_entity`）、`superseded_by` 指针、locale/lang、embedding 版本戳。
