# ADR-0018 上游同步边界：五条铁律与两条红线

- **状态**：已接受（2026-10-31，issue #129；本版按 `docs/audit/2026-10-31-open-issues-first-principles.md` §4.4 修正——票面铁律 5「promptMode 缺省 chat→code 语义翻转」经实测无仓内支撑，已改写为「本仓与上游同为 chat，差异在别处」；体量全部换成实测值）
- **关联**：#129（本 ADR 的来源票）、#113（同源同步票）、#107/#108（同期治理票，见文末「后果」）；上游 TencentCloud/TencentDB-Agent-Memory（本地快照 `.local/upstream-sync/v201`，只含 MemoryCore / agents / deploy，**不含 MemoryProxy**）；相关 ADR：ADR-0001（值信号租户口径）、ADR-0005（身份叙事层）、ADR-0006（凭据 SoT）、ADR-0008（召回门限刻度）
- **域词典**：[CONTEXT.md](../../CONTEXT.md) → 上游同步边界（upstream sync boundary）

## 背景

本仓是上游记忆系统（TencentDB-Agent-Memory）的分叉，之后长出了上游没有的一整层「灵魂记忆」语义：灵魂规约（ADR-0003）、身份叙事层（ADR-0005）、值信号落库口径（ADR-0001）、召回门限刻度（ADR-0008）、凭据 SoT（ADR-0006）。这些语义不是散点，而是**长在具体文件里**的：MemoryProxy 的五个 handler、`core/store/sqlite.ts`、`core/store/tcvdb.ts`、`core/hooks/auto-recall.ts`、`gateway/server.ts`。

上游同期做了几件结构性重构（票面与审计口径，本仓快照无法就地复核其最终形态）：

- 把 MemoryProxy 的五个 handler 拆成细粒度 stages / runners，并删除这五个文件；
- 把 `store/sqlite.ts`、`store/tcvdb.ts` 目录化为 `store/sqlite/{memory-store,skill-store}`、`store/tcvdb/{client,memory-store,skill-store}`；
- 新增 MongoDB 后端（`store/mongodb/memory-store.ts`）；
- 新增 `knowledge_source_credential` 等第二套凭据通道。

于是「跟随上游」在多数文件上是升级，在少数文件上等于**先把本仓能力删掉、再想办法补回来**，而且补不回来——因为上游的拆分前提里没有「灵魂列必须存在」「结论层 SQL 必须挂在召回前」这类不变式。每次同步都要重新论证一次「这个文件能不能照抄」，结论反复且会随讨论漂移，所以固化成边界：**五条铁律说哪些结构性变更不跟，两条红线说哪两个文件任何时候都不许整文件取上游。**

## 决定

### 铁律 1 — 不跟随 MemoryProxy 的 pipeline 重构

不采用上游把五个 handler 拆成 stages / runners 的结构，也不接受「删掉这五个文件」的合并。**判据是能力而不是文件**：灵魂规约注入、member-llm 成员上游解析、dsh 客户端适配都长在 handler 上——`MemoryProxy/src/anthropicHandler.ts:62-63`、`MemoryProxy/src/codexHandler.ts:59-60`、`MemoryProxy/src/handler.ts:60` 都 import `./member-llm/index.js` 与 `./member-llm/resolver.js`；dsh 适配在 `MemoryProxy/src/handler.ts:471`、`:479`、`:722`、`:726` 与 `MemoryProxy/src/credit-reporter.ts:77`。整文件取上游 = 这些能力一起消失。

### 铁律 2 — 不跟随 store 目录化

不采用上游把 `sqlite.ts` / `tcvdb.ts` 拆成 `store/{sqlite,tcvdb}/{client,memory-store,skill-store}` 的布局，也不接受「删除这两个大文件」。它们承载本仓独有的落库语义：ADR-0001 的值信号（`sqlite.ts` 的 `upsertValue` / `valuesCache` / `listValues`，含 `DO UPDATE` 全量替换缺陷的修复）、记忆图 links、R7 结论层 SQL、L1 FTS 门限与 `nativeMinRRF`。上游拆出来的 `memory-store` / `skill-store` 没有这些语义，拆完等于把不变式分散到上游不认识的模块里。

### 铁律 3 — 不引入第二套凭据真源

不采纳上游 `knowledge_source_credential`、也不采纳 JEV 的 `apiKeyEnv` / yaml `${VAR}` 通道与 task-draft 的 env 覆盖（ADR-0006 已把凭据 SoT 收敛到 admin-settings）。多通道的代价不是「多一个配置项」，而是「用哪把 key」在运行期变成不可判定的推断，且错误会以 401/越权/静默回落三种形态出现。

### 铁律 4 — 不引入 MongoDB 后端

`MemoryCore/src/gateway/server.ts` 的后端枚举只有 `sqlite` 与 `tcvdb`（`process.env.STORE_MODE === "sqlite" || process.env.STORE_MODE === "tcvdb"`，2026-10-31 位于 `:2355-2356`；行号随代码漂移，本 ADR 所有行号均为该日快照）。上游的 MongoDB 实现（票面口径 `store/mongodb/memory-store.ts`，本仓快照无此文件）完全不知道灵魂列：本仓的 SOUL 列由 `core/store/soul-columns.ts` 单一事实源展开，在 `sqlite.ts:63` 导入、`:111` 展开成 FTS 列定义、`:1475` 展开 L1 FTS 列清单。采纳 MongoDB = 灵魂列缺失、召回静默降级。**静默降级比启动失败更糟**，所以这里的取舍是「不支持」而不是「支持但可能降级」。

### 铁律 5（修正版）— 不存在的「promptMode 缺省翻转」

**本仓与上游的启动配置同为 `chat`，不存在「上游 code / 本仓 chat」的语义差异，因此不允许把任何一项同步决策挂在这条理由下。**

- 本仓：`deploy/global-images/start-memory-core.sh:81-86`（`# promptMode: chat（默认，通用聊天/教学场景）| code（代码工程场景，…）` + `promptMode: ${MEMORY_PROMPT_MODE:-chat}`）
- 上游快照：`.local/upstream-sync/v201/deploy/global-images/start-memory-core.sh:75-78`，逐字同文，缺省同样是 `chat`

票面原先写的「上游 `start-memory-core.sh:190-194` 是 code、本仓 `:75-78` 是 chat」在仓内不可复现（上游快照那份脚本只有约 80 行）。结论：**前提不成立，结论作废**。这不是说两边没有差异，而是说差异必须按具体语义另证（例如 promptMode 的消费者是否变化、code 分支下的提示词是否改动），不能再作为一条「同步边界」使用——保留会让后续同步者在错误前提下做决定。

### 红线 1 — `core/hooks/auto-recall.ts` 禁止整文件取上游

单文件取上游的后果是绕过 ADR-0008 的全部刻度门：上游的 `nativeBm25Search` 快路径在**结论层、图折扣、折叠、importanceGate 之前**就 return，等于把本仓精心排的召回次序整段跳过；而且 embedder 降级会改变 `effectiveStrategy` 分流，让「有没有向量」变成两条不同行为路径。红线内仍接受**手工迁移的单点补丁**（对 diff 逐条移植），禁止的是整文件替换。

### 红线 2 — `gateway/server.ts` 禁止整文件取上游

上游没有 `/v3/recall`（本仓快照 `.local/upstream-sync/v201/MemoryCore/src` 内 grep 零命中），整文件取上游会让 DS-RECALL-MERGE-001 的单点合并召回端点消失。本仓侧实证：`gateway/v2-router.ts:1893` 的关闭文案 `/v3/recall is disabled: memory.recall.v3Recall.enabled is false (code default)`，以及 `v2-router.ts:135` / `:301` / `:303` / `:584` / `:1839` 的引用点（`server.ts` 内没有独立的 `"/v3/recall"` 字面量，端点装配在 v2-router）。同红线 1：单点补丁可迁，整文件替换不可。

## 理由

- **为什么不跟 pipeline 重构**：拆成 stages×30 / runners×7 是**结构收益**，不是行为收益；本仓要的是灵魂注入与成员上游解析的确定性。整文件取上游等于让「能力挂在 handler 上」这一事实直接变成能力消失。
- **为什么不跟 store 目录化**：ADR-0001 的值信号、记忆图 links、R7 结论层 SQL、FTS 门限都在两个大文件里，且互相耦合（值信号与 FTS 列清单共用列定义）；拆目录会让这些实现点失去单一落点，之后每个同步都要在多文件间重新拼装不变式。
- **为什么禁止第二套凭据**：凭据是「唯一真源」类问题，第二套通道不是可选项而是缺陷源；ADR-0006 的收敛成本已经付过一次。
- **为什么禁 MongoDB**：本仓的召回正确性依赖灵魂列存在（`SOUL_COLUMNS` 展开成 FTS 列）；一个不知道这些列的后端只会静默降级，而静默降级在生产里表现为「记忆好像变笨了」，无法归因。
- **为什么铁律 5 必须改写而不是删掉**：这条是最容易复发的错误——一个听起来很具体的「语义翻转」会被反复引用。留着「同为 chat，差异在别处」既保留了「这里曾经踩过坑」的记忆，又堵住了错误引用。
- **为什么红线是「文件级」而不是「整仓禁止取上游」**：大部分 src 仍应跟随上游修 bug；红线只覆盖两个「上游结构与本仓语义完全耦合」的文件。把红线写成整仓禁令会让正常同步停止。
- **为什么用语义不变式而不是行号**：行号会漂（同期 `sqlite.ts` 7059→7134、`auto-recall.ts` 4312→4365 就是并行开发造成的漂移），铁律必须陈述「不许消失的能力」，由测试钉住能力，而不是钉住某一行。

## 后果

- **同步成本**：pipeline 与 store 目录化这两块基本不跟，上游在该处的 bugfix 需要手工挑拣并逐条移植；这是本 ADR 明确接受的代价。
- **门禁形态**：铁律 1/2/4 的判据是「能力存在性」（灵魂列、member-llm 解析、召回门限次序），不是文件存在性。红线 1/2 由既有测试兜底（auto-recall 门限用例、`v3/recall` 端点用例）；**若这些用例被删，红线就失效**，删用例必须走 review。
- **数字会过期**：本节体量是 2026-10-31 快照。任何以行数为论据的论证都应重测；权威数字以 `docs/audit/2026-10-31-open-issues-first-principles.md` §4.4 为准，本 ADR 只记录方法。
- **不在本 ADR 范围**：同步节奏与自动化（当前仍是人工比对 + 手工移植）、上游新功能的采纳标准（那是逐票决策）。另外 `CONTEXT.md` 的 ADR 索引尚未收录 0018 词条（该文件不属于 #129 的改动范围），索引维护留给持有 CONTEXT.md 的票。
