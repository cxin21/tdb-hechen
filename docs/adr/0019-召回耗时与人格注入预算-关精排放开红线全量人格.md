# ADR-0019 召回耗时与人格注入预算：关本地精排、放开红线、全量人格一次注入

- **状态**：已接受（2026-11-01，来源：用户令「召回、红线都修复一下，还有灵魂注入，能否全量注入呢」；本机四域活体测试同日取证）
- **关联**：ADR-0013（rerank 题内相对尺子）、ADR-0014（删除 rerank 排序加权混排）、ADR-0005（身份叙事层）、ADR-0003（灵魂规约）；实现面 `MemoryCore/tdai-gateway.yaml`、`D:/TDB/data/config-override.json`、`dsh-plugin/src/{config,index,recall-source}.ts`
- **域词典**：[CONTEXT.md](../../CONTEXT.md) → volatile 注入块 / soul 渲染

## 背景（2026-11-01 活体取证）

三个互不相同、但互相掩盖的故障叠在同一条链路上：

1. **召回从没成功过**：`/v3/recall` fresh 查询 24 次 **0 次 200**（10 次 504@5s + 14 次连接失败），单条时间线为 query-expand 438ms → embedding 397ms → L1 检索 130ms → **6.2s 空档**。空档来自本地精排：生产 `rerank:{enabled:true,provider:"local",timeoutMs:5000,candidates:32}`，而本机实测 `bge-reranker-base`（transformers.js 4.3.1，dtype q8）**单条 145–163ms、32 条 4637–5224ms**，恒超 5000ms ⇒ 日志里每次都 `[rerank] provider=local 返回 null，降级原序`。**质量零收益，净耗 5s。**
2. **精排的耗时救不回来**：批处理实测 batch=4/8/16/32 分别 3663/4031/4882/4501ms（串行 4637ms，仅快 3%），且批量与串行单条分数最大差 ~1.07 logit；`threads=4`、`docCap=256` 更慢。这台被节流的 CPU 是算力瓶颈，不是调用开销。
3. **人格从没进过 prompt**：core 渲染 3384 字符人格（`## 此刻的我` 2509 / `## 不可逾越（红线）` 815 / `## 当下的状态` 42），但插件 soul 预算只有 600 字符 ⇒ 真实注入 3 个会话**均 536 字符**、切在句子中间、**在红线段之前**（`含红线段=false`）。同时 core 侧 `strictRuleDedup.maxLines: 8` 把 16 条红线砍成 8 条（`DEBUG [soul-dedupe] strict_rules capped 8/16`）。

## 决定

0. **载体说明**：`MemoryCore/tdai-gateway.yaml`（`.gitignore:142`）与 `D:/TDB/data/config-override.json` 都是**本机部署配置、不入库**，所以本条决策的耐久载体就是这份 ADR；插件侧（`dsh-plugin/**`）的预算是入库的默认值。
1. **关闭本地精排**（`config-override.json` → `rerank.enabled: false`）。它在这台机器上物理不可能在预算内完成；开着只是把每次召回推过 5s 再降级成原序。重新启用的前提是**换掉串行 CPU 推理**（云端 rerank 或更强的算力），而不是调大 timeout——调大 timeout 等于用 5s+ 的轮次延迟换零质量。
2. **放开红线上限**（`tdai-gateway.yaml` → `strictRuleDedup.maxLines: 8 → 16`）。红线是硬约束承载面，「只进一半」比「不治理」更危险：模型以为看到了全部规则。
3. **插件侧全量注入人格**：`volatile.soul.maxChars 600 → 4400`（装得下 16 条红线全渲染后的 ~4200），`volatile.maxChars 1500 → 6000`（4400 + 记忆 ≈900 + 能力段 ≈700）；`soul.enabled: false` 时记忆退回 `min(maxChars, 1500)` 旧口径，避免关掉人设反而让记忆吃满 6000。
4. **每会话只注入一次完整人格**（新开关 `volatile.soul.oncePerSession`，缺省 true）。块是追加进会话历史的 `user/message`，第一次那份还在上下文里，所以不必每轮重付 4200 字符；`soulVersion` 变化（人格被重新蒸馏）时再注入一次。关掉此开关=回到「每轮都带人格」。
5. **裁剪改成红线优先 + 整行**（`clipSoulIdentity`）。预算实在不够时先整段保留 `## 不可逾越（红线）`，再按文档顺序补其它段；被截的段落结尾加 `…`，绝不把一行切成两半（旧实现正是把人格切在句子中间，才让「截断」看起来像「人格就长这样」）。

## 后果

- 召回回到 ~1.3–2.2s（expand+embed+L1），落在插件 `recallTimeoutMs: 2500` 内 ⇒ soul 段真正进入 prompt；关精排不改质量排序（今天本来也一直是原序）。
- 每轮 prompt 增量：首轮 +4200 字符（一次性），之后 +0；关掉 `oncePerSession` 则每轮 +4200。
- 代价与残留：本机**没有可用的精排**，`rerank` 段留在配置里但关闭，重新启用需 ADR 级别的算力/通道决策；core 崩溃取证（同日 watchdog 三次重启、无异常栈）**不在本 ADR 范围**，仍未定位。
- 观测锚：core `[soul-dedupe] strict_rules capped N/16` 应消失（无 cap 命中即不打印）；插件每轮 debug 行 `soulChars`（首轮 >4000、之后 0）与 `soulVersion`。
