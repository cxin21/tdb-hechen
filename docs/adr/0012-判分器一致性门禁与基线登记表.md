# ADR-0012 判分器一致性门禁与基线登记表

- 状态：接受
- 日期：2026-10-28
- 关联：#140（父票 #134 第二波写入治本）、#135（judge 对齐复核数据）、ADR-0008（召回门限口径先例：口径变更必须显式化）
- 落点：`MemoryCore/scripts/lib/bench/judge.mjs`、`baseline.mjs`、`rejudge.mjs`、`bench-{compare,gates,ranking,baseline,rejudge}.mjs`、`fit-fusion-weights.mjs`

## 背景

bench 的档位报告里，`genCorrect`/拒答这类指标由 LLM 判分器给出，而 `turnCov@5`/MRR 由召回本身决定。判分器一换，同一批答案的判对率就换了一把尺子量：

- 2026-10-26 的 b0-base/b1-off 由 scm-flash 判分（38.9% / 70.0%）；
- 10-27 起的档位由 MiniMax-M3.1-Flash 判分；
- 跨判分器直接配对，把 w3b vs b1-off 的 +6.7pp（p=0.146）虚增成 **+14.4pp（p=0.0023）**——差出来的 +7.8pp 是尺子差异，却被当成方法收益写进结论，随后被迫作废。

人工复核能救一次，救不了每一次：报告名只有时间戳，`b1-off` 这个档位名在两种判分器下各存在一份，靠人的记忆分辨不出该配哪一份。

## 决定

### 1. 配对前先比判分器身份（四个工具统一）

身份 = `config.judgeModel` + `config.judgePromptVersion`（+ `judgeHost` 仅展示）。判定与渲染集中在 `scripts/lib/bench/judge.mjs`（纯函数、零 IO），`bench-compare` / `bench-gates` / `bench-ranking` / `fit-fusion-weights` 一律调用，不各写一套。

| 情况 | 行为 | 退出码 |
| --- | --- | --- |
| 同判分器（模型 + 提示版本一致） | 正常判定 | 0（gates 仍按门禁给 0/1） |
| 跨判分器，或身份未记录但报告含判分行 | 拒绝判定：打印两侧判分器、配置差异、**可执行修复路径**；判对/拒答 Δ 不出数 | **3** |
| 同上 + `--allow-cross-judge` | 放行并标注「豁免 / 仅参考」；gates 的判对门禁记 SKIP，不计入门禁 | 0 |
| 两侧都无判分行（retrieval-only 档） | 放行——这份比较本来不涉及判分器 | 0 |
| `fit-fusion-weights` 跨判分器 | 不配对：不出 Δ、不给 E2 门禁结论，只并列展示 turnCov/sessionCov/mrr | 3 |

退出码 2 保留给「用法/读文件错误」，与拒判（3）分开，调用脚本能据此区分「跑错了」和「数据不可比」。

### 2. 拒绝必须带出口（不做「一律拒绝」）

拒绝只是止血，治本是把尺子对齐。拒判输出固定附带两条路径：

1. **对齐基线**：`bench-baseline resolve --judge <model>` 取「同 judge 基线」；`bench-gates auto <trial>` 直接用登记表里的同 judge 基线（不再靠文件名猜）。
2. **对齐旧报告**：`bench-rejudge <旧报告.json>` 用报告里已存的答案按当前判分器重判——只花 N 次判分调用，不重跑召回/生成/embedding；写 `config.rejudgedFrom` 溯源。

这也是为什么不去「关掉 rerank 之类开关回避问题」：要修的是归因口径，不是把能力关掉。

### 3. 基线登记表是「同 judge 基线」的单一真相源

`MemoryCore/.eval-data/bench/lme-baselines.json`（与 `lme-manifest.json` 同级、**入库**）：

- 槽位 = `(tag, manifest basename, dataset)`，三处（登记/门禁/重判）用同一个 `sameSlot` 判等；
- 每条记录 `judgeModel`/`judgePromptVersion`/`judgeHost`/`answerModel`/`repoCommit`/`report`/判对/coverage，**从 rows 重算**而不是抄 overall（重判后会过期）；
- `gateBaseline: true` 标记该 judge 槽位的门禁基线（一个 judge 只有一个）；`bench-baseline check <报告>` 判定 `ok`/`judge-changed`/`missing`，变更 judge 时强制重跑基线，而不是静默错配；
- 报告 JSON 本身是本机 `.eval-data` 产物、不入库，所以登记表只存指针：异机 clone 后指针悬空时 `bench-gates --base auto` 给「重新登记/拷回报告」的提示并退出 2，不抛 ENOENT 栈。

### 4. 配置差异用黑名单，不用白名单

「这一对到底只差一个因子吗」由 `configDiff` 回答：比对两侧 `config` 的键并集，只排除判分器身份 / `tag` / `manifest` / `dataset` / 溯源字段。新增实验旋钮（rerankOverride、candidateK、fusion、presentTemporal…）默认会被看见，不会静默输出「无差异」。

## 后果

- **变慢的地方**：跨判分器的历史配对现在会失败。这是预期——那类结论本来就不该成立；要么登记同 judge 基线，要么重判旧报告，要么显式 `--allow-cross-judge` 承认它只是参考。
- **需要维护的东西**：每次换判分器，必须重跑并登记基线（一条命令），否则 `--base auto` 会以 judge-changed 拒判。
- **可验证性**：重判把「判分器贡献」与「答案贡献」拆开——b1-off 同一批答案重判到 MiniMax 是 68.9%（scm-flash 70.0%，-1.1pp），说明 70.0%→77.8% 的 +7.8pp 主要是答案侧（commit 差异），但方向与幅度必须实测、不能假设为 0。
- **回归保护**：`__tests__/bench-judge.test.ts`（31 例，纯函数）+ `__tests__/bench-judge-cli.test.ts`（7 例，真实 CLI 的 exit 3 与修复路径文案）。

## 被否决的选项

- **只加警告、不改退出码**：CI/脚本会照样把跨判分器数字写进结论，等于没门禁。
- **一律拒绝跨判分器比较**：把「不可比」当成「不许看」，会逼人绕过工具手算；`--allow-cross-judge` + retrieval-only 放行是刻意留的出口。
- **只靠 docs 表格记 judge 归属**：docs 是叙述，门禁要机器可读的槽位（tag/manifest/dataset/judge）。
- **重跑整个基线来对齐 judge**：贵且不必要；答案已存在报告里，重判即可。
