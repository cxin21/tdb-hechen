## 4. 发现一（压倒性）：strict_rule 红线重申常驻霸位
**每条 query 的召回前 8 行都是完全相同的 8 条 strict_rule 红线记忆**（零删除/typecheck 基线/无依据不擅为/关票亲跑/唯一仓库 SOP/测试临时目录/英文定向/关票端到端证据）。
- 霸位行 = 32×8 = **256/370 = 69.2%**，行信息率零（对任何任务 query 均为 none）。
- 机制候选（待立票取证）：1) 这些行源自 **soul-event 红线重申事件被 capture 管线持久化为 L1 instruction**（每轮对话都注入 soul-event → capture 入库）；2) 召回侧霸位 = significance 0.8（SIGNIFICANT 词表「必须/务必/核心/全局」命中）+ recencyBoost（last_recalled_at<24h 强化 0.03）+ coreRef instruction 通道加权 + 8 行高度同质无多样性打散。
- 这正是 T4 四类病灶之外的**新病灶五：脚手架事件入记忆+常驻霸位**——查询侧污染的升级形态（不止污染单条 query，而是污染所有 query）。

## 5. 发现二：剔除霸位后，修复效果真实显著
